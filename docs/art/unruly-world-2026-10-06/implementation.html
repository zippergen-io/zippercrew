Communication rules

Local activity bubbleActual protocol object
Rounded white contour with a small tail. Shows local activity such as “Inspecting changes.” No sequence number or received badge.Cream folded card/folder with a small category accent. Shows the actual message label, sequence when supplied, sender/recipient and authoritative pending/received state.

Task, Proposal, Review and Guidance use the same carrier grammar. A decision request can have a diamond tab. Type labels remain live text and come from the runtime; illustrative marks on a concept sheet are not message payloads. Keep the Human's bound teal notebook visually distinct from loose cream protocol cards.

  • Start at the participant's hand dock (x+65, y−85), move into a clear escape column near x+110, then across the y226 lane. The column sits beyond the local bubble's width.
  • Limit the room to two travelling cards at once. Queue additional observed sends visibly as a folder/count and keep every item in the message log; the cap affects animation only.
  • Same-room cards land at the recipient dock. Cross-room cards reach a connector labeled with the recipient and destination room. A room switch shows the same message ID in its destination; it does not manufacture another send.
  • Visual arrival never marks a protocol receive. Update “Received” only when the authoritative receive_id or equivalent runtime receipt arrives.
  • Room tabs show real pending counts and named destinations. Keep the current view stable; offer “Follow message” or a recipient click instead of moving the camera for every event.
  • Use one replay-safe message store outside the room view. Deduplicate by runtime identity/version, retain off-screen messages and update them while rooms are unmounted.
  • With reduced motion, place cards directly at the receiving dock or room port and retain their real status. Provide the same information in accessible DOM/log controls.

Phaser integration in this repository

The app currently loads Phaser 3.90.0. Keep that renderer for this change. Existing scene.js mirrors runtime snapshots and accessible controls; dollhouse-layout.js owns presentation geometry; dollhouse-room.js renders, projects overlays and animates messages. These are the integration seams.

  • Layout: evolve buildLayout into a room graph plus room-local anchors, furniture footprints, destinations and message ports. Reuse blocked, clearSegment and route within each room. Cross-room walking routes are paths to a doorway plus a graph transition, not straight segments through walls.
  • Participant identity: the current scene maps people, bindings and DOM controls by role name. Multiple Implementers or Reviewers need stable participant-instance IDs throughout those maps, selected state and endpoint resolution. Do not synthesize IDs by changing incoming message labels.
  • Runtime prerequisite: state.py currently keeps three role-keyed participant states. The 5/8-person layouts demonstrate presentation capacity. Live multi-instance crews also need runtime configuration/state/bindings to expose those distinct participants and their actual protocol endpoints.
  • Camera: current resize() scales a 1160×700 container and pans it. Either retain that approach with one selected 960×640 room, or move the world to a Phaser camera with room bounds. Use one projection transform for sprites, hit areas and DOM bubbles. Crew count changes room membership, not zoom. Phaser exposes camera bounds, scroll and zoom independently; see official camera guidance.
  • Depth: use background, back-wall props, furniture/characters ordered by floor depth, protocol objects, and DOM overlays. If using the existing world Container, sort its children as the current scene does; nested Containers do not interleave their children with external siblings. See official Game Object depth guidance.
  • Assets: load shared furniture and message art as atlases in preload. Names/status/brief content stay live DOM or Phaser text. Phaser's loader supports atlas image/JSON pairs; see official loader guidance.
  • Life: bind idle, walk (2–3 frames), work/laptop, inspect, listen, receive and small success poses to observed state. Blink/head tilt/sip are sparse local animations. Motion does not enable workflow actions. Export final cast atlases only after a richer direction is chosen.

Build order and acceptance checks

  1. Choose the richer cast revision, then draw the approved hub, maker and quiet module kit with fixed pivots. Remove concept-only grain/shading and bake no text.
  2. Implement one hub with separated floor collisions, sprite bounds and overlay lanes; verify full bodies, laptop hands and seated occlusion at typical app dimensions.
  3. Add room-local navigation and unique participant identity; exercise the 5/8-person room graphs before connecting extra runtime agents.
  4. Connect the message store and real event envelopes; exercise send, off-room receive, pending, replay and reduced-motion cases.
  5. At 3, 5 and 8, verify unchanged sprite heights, clear walking routes and distinct activity/card grammar. Inspect 100%, 60% and 40% cast scale with the selected richer art. Card labels and role names should remain live text at a readable screen size.

Preferred direction: Linked Studio. Window Atelier is a useful optional window/furniture module; Coffee Hinge contributes a small shared idle corner. Pocket Loft is an alternative with higher navigation complexity, so it is not the production base. The three richer cast sheets are focused refinement options and are not automatically selected by the room study.
